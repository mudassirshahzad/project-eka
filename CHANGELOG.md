## [Unreleased] — v0.6.1 Engineering Excellence & Repository Governance

### Added (v0.6.1 — Engineering Excellence & Repository Governance)

Post–Phase-5 milestone, explicitly **not** Phase 6 — closes findings from an independent, adversarial audit conducted after v0.6.0 shipped ("act as an independent Staff Engineer... challenge the implementation, not defend it"). No new business functionality, no new platform capability; every change closes a specific, numbered audit finding, or documents why a finding is intentionally deferred.

- **CI/CD foundation** — `.github/workflows/build.yml` runs `gradle clean build` (full test suite + all 8 ArchUnit rules) on every pull request and every push to `main`, the repository's first automated gate; provisions Gradle 8.12 via `gradle/actions/setup-gradle` rather than a committed wrapper, matching existing local-dev convention. Branch protection (required status check, PR-before-merge, no direct pushes/force-pushes to `main`) is specified with an exact `gh api` command in new `docs/governance/branch-protection.md` — not applied automatically, since a live GitHub repository setting isn't something to change from inside the repository itself (ADR EX01)
- **Exception handling hardening** — `GlobalExceptionHandler` now extends `ResponseEntityExceptionHandler`; Spring MVC's own framework-level exceptions (malformed JSON, a non-UUID `@PathVariable`, an unsupported HTTP method, and ~15 others) resolve to the correct 4xx `ProblemDetail` response instead of falling through to the generic `Exception.class` → 500 handler. Verified via `javap` against the actual `spring-webmvc-6.2.7.jar` that Spring resolves `@ExceptionHandler` methods by exception-type specificity across the whole class hierarchy, not declaring-class proximity, so no reordering was needed; the one exception type this class already handled (`MethodArgumentNotValidException`) is preserved via the protected `handleMethodArgumentNotValid` override hook the base class exposes for exactly this purpose, not a second competing `@ExceptionHandler` (which would be an ambiguous mapping) (ADR EX02)
- **Version alignment** — `build.gradle`'s `version`, hardcoded to `1.0.0-SNAPSHOT` since the very first commit and never once updated across six tagged releases, is now `0.6.1` and the single source of truth. `springBoot { buildInfo() }` surfaces it at `/actuator/info` as `info.build.version` with zero manual sync, replacing the hand-maintained `info.app.version` string (ADR EX03)
- **JWT startup validation** — `JwtProperties`'s compact constructor now rejects an HS256 secret shorter than 32 bytes (256 bits) and a non-positive token expiry, eagerly at application-context startup (`@ConfigurationPropertiesScan` instantiates it as a singleton during context refresh). Before this, a misconfigured secret would start the application successfully and only fail — with a JJWT `WeakKeyException`, not an operator-facing message — on the first real login request (ADR EX04)
- **Login rate limiting** — new `LoginRateLimiter` (`api.security`): an in-memory, per-IP, fixed-window counter (10 attempts/minute by default, configurable) guarding `POST /api/v1/auth/login`, checked before any credential verification. Deliberately in-process, not Redis- or Bucket4j-backed — this application runs as a single instance today, and building distributed rate-limiting infrastructure for a deployment shape that doesn't exist would be over-engineering this milestone's own brief explicitly warned against. A `@Scheduled` sweep every 5 minutes bounds memory over a long-running process (ADR EX05)
- **Request size protection** — new `RequestSizeLimitFilter` (`api.security`) rejects any request whose `Content-Length` exceeds `app.request.max-body-bytes` (default 1 MiB) before Spring MVC or Jackson ever process it — neither Tomcat's `maxPostSize` (form-parameter parsing only) nor any Spring MVC property bounds an arbitrary `@RequestBody` JSON payload by default. Constructs its `ProblemDetail` rejection body directly (a `Filter` runs before `DispatcherServlet`, outside `@ExceptionHandler` reach) to keep the response shape identical to every other error response (ADR EX06)
- **Stale documentation fix** — `SecurityConfig`'s class Javadoc stated "Authorization is explicitly out of scope... that is P05.3's job" a full two milestones after P05.3 actually shipped `AuthorizationInterceptor` — corrected; found via the independent audit's "verify documentation against the actual code" instruction, not by this project's own prior doc-sync passes, which had focused on `PROJECT_STATE.md`/`DECISIONS.md` rather than in-code comments on files touched by earlier milestones (ADR EX07)
- **Dead Use Case layer resolved** — evaluated per-class rather than mechanically: `CreateConversationUseCase` is now the class `ConversationController.createConversation` actually calls (previously the controller bypassed it entirely, going straight to `ConversationApplicationService`, while the unreached use case independently re-validated the exact title-length rule the REST DTO already enforced). The title invariant itself now lives in the `Conversation` domain aggregate (`Conversation.create`/`.rename`, new `MAX_TITLE_LENGTH` constant, `IllegalArgumentException` on violation) — the DDD "always-valid aggregate" way, enforced regardless of caller; `Conversation.reconstitute` deliberately does not re-validate, so tightening this rule later can't break loading of previously-valid rows. `GetConversationUseCase`/`ListConversationsUseCase` were deleted outright — both were pure pass-throughs adding nothing beyond null-checks that were already unreachable (identity is JWT-sourced) and a redundant `@Transactional(readOnly=true)`; wiring the controller through them would have been ceremony with zero behavioral value. `DeleteConversationUseCase` is left as-is: correctly designed, still unreached, because adding the `DELETE` route it needs would be new capability, out of this milestone's scope (ADR EX08)
- **Document ingestion endpoint — decision recorded, not implemented** — the audit's finding that document ingestion has no REST endpoint is intentionally deferred: adding `POST /api/v1/documents` is new platform capability, explicitly forbidden by this milestone's "zero scope creep." `README.md` corrected in the meantime so it no longer claims document upload as unqualified "✅ Implemented" without the REST-reachability caveat (ADR EX09)
- **Application Dockerfile** — new multi-stage `Dockerfile` (`gradle:8.12-jdk21` build stage, `eclipse-temurin:21-jre-jammy` runtime, non-root user, tests skipped since CI already runs them) closes the "no Dockerfile for the app itself" gap — `docker-compose.yml` already containerized Postgres/Weaviate/Ollama but not the application. `docker-compose.yml` itself was deliberately not touched — wiring the new image into it is a deployment-topology decision this milestone's "keep it simple, do not redesign deployment" instruction rules out. **Not empirically verified with a real `docker build`** — no Docker daemon was available in the implementing environment; disclosed here rather than assumed working (ADR EX10)
- ADRs EX01–EX10 frozen (see `.claude/DECISIONS.md`)
- 17 net new tests (21 added, 4 removed as obsolete): `JwtPropertiesTest` (new file, 5) — weak-secret/null-secret/non-positive-expiry rejection, boundary acceptance at exactly 32 bytes; `LoginRateLimiterTest` (new file, 4) — under-limit, over-limit, independent per-key tracking, window reset via a controllable `Clock`; `RequestSizeLimitFilterTest` (new file, 2) — pass-through vs. 413 rejection without reaching the filter chain; `domain.conversation.ConversationTest` (new file, 7) — the domain aggregate's first dedicated test, covering the relocated title invariant including proof `reconstitute` never re-validates; `ConversationControllerTest` (+3) — non-UUID path variable and malformed JSON body both now 400 not 500, plus updated mocking of `CreateConversationUseCase`; `AuthControllerTest` (+1) — rate-limit-exceeded returns 429; `CreateConversationUseCaseTest` (−4, simplified) — title-boundary tests moved to `ConversationTest` since that validation moved to the domain; `RagEndToEndIT` — `/actuator/info` assertion extended to prove `info.build.version` is actually populated. 623 total tests, 0 failures. ArchUnit: 8/8, no new layering violations.

## [0.6.0] — 2026-08-16 — Phase 5 Complete

### Added (P05.5 — Operational Hardening & Phase 5 Completion)

Fifth and final milestone of Phase 5 — a release-candidate/production-readiness pass, not a feature milestone. Zero new platform capability; every change either closes a gap an earlier milestone explicitly deferred or fixes something this milestone's own repository audit found. Where a fix would have required real architectural expansion (a configurable Weaviate HTTP client), it is documented as deferred technical debt instead of implemented, per this milestone's own scope constraint.

- **Upload pipeline transaction boundary** — `UploadDocumentUseCase` is no longer `@Transactional` at the class level; `DocumentApplicationService`/`ChunkApplicationService` each already carry their own `@Transactional`, so removing the outer wrapper gives every DB-touching step its own short transaction instead of one long transaction spanning Tika parsing, file storage, an Ollama embedding call, and Weaviate indexing. Pipeline failures now call the domain's own `Document.markFailed(String)` — present in the domain model since it was designed, but never actually called until now — persisting a `FAILED` status with the error message instead of silently leaving a document stuck in whatever status it last reached. Closes the P04.13.8-flagged "genuine technical debt" item (ADR HD01)
- **Tenant isolation gap closed** — `ConversationApplicationService.renameConversation`/`.deleteConversation` (and `RenameConversationCommand`/`DeleteConversationUseCase`) now take and verify `TenantId`, identically to the three methods P05.3 already covered. Neither method has a REST route yet; fixed ahead of exposure rather than waiting for one, closing the exact gap `PROJECT_STATE.md`'s Deferred Items table had tracked since P05.3 (ADR HD02)
- **Ollama HTTP timeout hardening** — new `infrastructure.config.HttpClientTimeoutConfig` registers a `RestClientCustomizer` bounding connect/read timeouts (`app.ollama.connect-timeout-ms`/`read-timeout-ms`, default 5s/60s) on the Boot-managed `RestClient.Builder` Spring AI's `OllamaApiAutoConfiguration` consumes — confirmed via direct bytecode inspection of the Spring AI 1.0.0 autoconfiguration jar, not assumed from documentation. The equivalent fix for Weaviate was investigated the same way and found not to exist: `WeaviateVectorStoreProperties` exposes no timeout property, and the auto-configured `WeaviateClient` bean has no customization hook comparable to `RestClientCustomizer`. Documented as deferred technical debt rather than implemented, since a fix would require overriding the auto-configured client construction entirely (ADR HD03)
- **Exception consistency** — `RetrievalService.doRetrieve()` now catches infrastructure-level `RuntimeException`s (`HybridRetrievalException`, `QueryRewriteException`, `VectorStoreException`, and subtypes — all of which extend plain `RuntimeException`, not `RetrievalException`) and rewraps them as `RetrievalException`, so `GlobalExceptionHandler`'s existing 502 mapping actually reaches them instead of falling through to a generic, unexplained 500. Separately, `GlobalExceptionHandler` gained a dedicated `InvalidRetrievalRequestException` → 400 handler, registered ahead of the broader `RetrievalException` → 502 handler despite the subtype relationship (Spring dispatches to the most specific handler automatically) — an oversized or blank query was previously misreported to the caller as an upstream 502 rather than the caller's own 400-shaped mistake (ADR HD04)
- **Configuration hardening** — `spring.datasource.password` no longer defaults to `ka_pass` in the base/production profile (mirrors the existing `JWT_SECRET_KEY` pattern exactly); `dev` and `test` profiles each set their own explicit value. New opt-in `server.port`/`management.server.port` properties (`SERVER_PORT`/`MANAGEMENT_PORT` env vars) let an operator isolate actuator endpoints onto a separate embedded connector outside the app's JWT-based `SecurityFilterChain` — a no-op by default (management stays on the same port), partially addressing the P05.4-deferred "`/actuator/metrics` requires a JWT rather than being scraped anonymously" item (ADR HD05)
- **Dependency cleanup** — removed `spring-boot-starter-aop` and MapStruct (`mapstruct`, `mapstruct-processor`, `lombok-mapstruct-binding`) from `build.gradle` after confirming zero usage repo-wide (`@Aspect`/`org.aspectj`, `@Mapper` — all zero matches across main and test sources) and verifying a full clean build + test run succeeds identically without them (ADR HD06)
- ADRs HD01–HD06 frozen (see `.claude/DECISIONS.md`)
- 13 new tests: `UploadDocumentUseCaseTest` (+2) — failure marks the document `FAILED` with the error message and still rethrows; successful pipeline never calls `markFailed`; `ConversationApplicationServiceTest` (+4) and `DeleteConversationUseCaseTest` (+1) — tenant-check coverage for `renameConversation`/`deleteConversation`, mirroring the P05.3 pattern; `HttpClientTimeoutConfigTest` (new file, 2) — customizer applies cleanly to a real `RestClient.Builder`, distinct timeout arguments produce distinct customizers; `RetrievalServiceTest` (+2) — infrastructure exceptions from both `RetrievalPort` and `QueryRewritePort` are wrapped as `RetrievalException`; `GlobalExceptionHandlerTest` (new file, 2) — `InvalidRetrievalRequestException` → 400, plain `RetrievalException` → 502. 606 total tests, 0 failures. ArchUnit: 8/8, no new layering violations. **Phase 5 (Application Platform) is now complete.**

### Added (P05.4 — Observability Foundation)

Fourth milestone of Phase 5. Makes the application observable, diagnosable, and operationally supportable using Spring Boot's native Actuator/Micrometer/Observation stack — no custom monitoring infrastructure, no new dependency (`spring-boot-starter-actuator` and `micrometer-registry-prometheus` were already scaffolded ahead of this milestone). Explicitly excludes distributed tracing platforms, Prometheus/Grafana deployment, ELK/OpenSearch/Splunk, and operational hardening — those are future phases or deployment environments, not application code.

- **Actuator** — `/actuator/health` and `/actuator/info` added to `SecurityConfig`'s public endpoints (`/actuator/metrics`/`/actuator/prometheus` deliberately stay behind the existing JWT boundary — ADR OB01); `management.endpoint.health.probes.enabled` turns on `/actuator/health/liveness` and `/actuator/health/readiness`; `info.app.*` populates `/actuator/info` with static app identity (`management.info.env.enabled: true` was required for this to actually surface — Spring Boot defaults that off)
- **Custom health indicators** — `OllamaHealthIndicator`/`WeaviateHealthIndicator` (new `infrastructure.observability` package) each issue one short-timeout (2s) HTTP check — Ollama's root URL, Weaviate's `/v1/.well-known/ready` (the same endpoint `docker-compose.yml`'s own container healthcheck already uses) — contributing to `/actuator/health` and the new `readiness` health group, deliberately not `liveness` (an unreachable external dependency isn't a broken app process). `@Profile("!test")`-excluded rather than toggled off via `management.health.*.enabled`, after that toggle was found — by this milestone's own `RagEndToEndIT` health-endpoint test — not to reliably apply to hand-written indicators (ADR OB05)
- **Metrics** — `RetrievalService.retrieve()`, `GenerationService.generate()`, `RagOrchestrationService.handleUserMessage()` each now run inside an `eka.retrieval`/`eka.generation`/`eka.orchestration` Micrometer `Observation` — a timer today via Spring Boot's auto-registered `DefaultMeterObservationHandler`, and trace-ready with zero further code changes once distributed tracing (out of scope) is ever added, directly satisfying "prepare for future distributed tracing without implementing it." New failure counters: `eka.auth.failures{type=token|credentials}` (`JwtAuthenticationFilter`, `AuthenticateUserUseCase`) and `eka.authz.failures{reason=role|ownership}` (`AuthorizationInterceptor`, `ConversationApplicationService`'s tenant-mismatch branch). Request counts, response times, and error counts are **not** separately instrumented — Spring Boot's auto-instrumented `http.server.requests` timer already provides these; duplicating it would be exactly the "duplicated metrics" this milestone's quality gate forbids. No metric anywhere is tagged by a raw tenant/user/conversation ID — unbounded cardinality is a well-known Micrometer/Prometheus anti-pattern (ADR OB02)
- **Correlation IDs** — new `api.observability.CorrelationIdFilter`, registered ahead of every other filter in `SecurityConfig`'s chain, including Spring Security's own first filter (`DisableEncodeUrlFilter`) — not just ahead of `JwtAuthenticationFilter` — so even a request Spring Security itself rejects still logs and responds with a correlation ID. Generates a UUID or reuses a caller-supplied `X-Correlation-Id` header, but only if it matches a safe pattern (`^[A-Za-z0-9._-]{1,64}$`) — an unvalidated header would let a client inject CRLF sequences into every log line for the request (log injection) or supply an unbounded string. Propagated via MDC for the request's duration (cleared in `finally`) and echoed on the response header only — not embedded in `ProblemDetail` bodies, since the header already covers every response uniformly, success or error, without seven repetitive `GlobalExceptionHandler` edits (ADR OB03)
- **Structured logging** — `logging.structured.format.console: ecs` (Spring Boot 3.4+ native Elastic Common Schema JSON), active in every profile including `dev`/`test` — no new logging library, no custom encoder. MDC (including the correlation ID) is automatically surfaced as structured fields with zero per-call-site code. The existing Security/Logging Policy table (`PROJECT_STATE.md`) — what data may ever appear in a log line — is unchanged; this milestone changes the *shape* of log output, never *what* is logged (ADR OB04)
- **Self-review fix:** `AuthorizationInterceptor` had metric counters for both denial branches but no log statement at all, while `ConversationApplicationService`'s ownership-check counterpart logged at WARN — an inconsistency for anyone troubleshooting a spike in `eka.authz.failures{reason=role}`. Added a DEBUG-level log line to both denial branches, including which roles were required vs. held (role names are business-domain labels, not sensitive — unlike the response the caller sees, which stays deliberately generic per ADR AZ03)
- ADRs OB01–OB05 frozen (see `.claude/DECISIONS.md`)
- 20 new tests: `CorrelationIdFilterTest` (6) — ID generation vs. reuse, unsafe/overlong header rejection, MDC population during the chain and cleanup after (including when downstream throws), response header echo; `OllamaHealthIndicatorTest` / `WeaviateHealthIndicatorTest` (3 each) — reachable→UP, server error→DOWN, unreachable host→DOWN without throwing, via `MockRestServiceServer`; metrics assertions added to `JwtAuthenticationFilterTest`, `AuthenticateUserUseCaseTest`, `AuthorizationInterceptorTest`, `ConversationApplicationServiceTest` (one new counter-increment test each); constructor-guard tests added for the new `ObservationRegistry`/`MeterRegistry` parameters on `RetrievalService`, `GenerationService`, `RagOrchestrationService`; `RagEndToEndIT` gained 4 tests against the real, fully-wired app — orchestration timer + `http.server.requests` actually recorded after a real request, correlation ID header present even on a `permitAll` endpoint, `/actuator/health` and `/actuator/info` publicly reachable. 593 total tests, 0 failures. ArchUnit: 8/8 — `api.observability`/`infrastructure.observability` introduce no new layering violations

### Added (P05.3 — Tenant & Role Authorization Boundary)

Third milestone of Phase 5. Authentication (P05.2) answers "who is the user"; this milestone answers "what are they allowed to do" — a role-authorization boundary at the REST layer plus a defensive, explicit tenant/ownership check in the application layer. Deliberately narrower than CLAUDE.md's target-architecture "Authorization Filter" (a retrieval-pipeline stage doing fine-grained, metadata-based content filtering) — that remains a separate, unbuilt `ROADMAP.md` Future item; this milestone is the REST-boundary half only.

- `api.security.AuthorizationInterceptor` (new) — a `HandlerInterceptor`, not a `Filter` (unlike `JwtAuthenticationFilter`), registered against every `/api/v1/**` route by new `api.config.WebMvcConfig`. Reads a new `@RequireRole` annotation off the target controller method and denies (`AccessDeniedException`) if the caller's roles don't intersect; a method with no annotation is unrestricted. Deliberately never re-validates resource ownership itself — see below (ADR AZ01)
- `ConversationController.createConversation`/`.sendMessage` now require `@RequireRole({USER, ADMIN})` — `VIEWER`/`AUDITOR` are read-only. `getConversation` carries no role restriction (ADR AZ02) — **this role-to-action mapping is a new business rule introduced by this milestone**, since none previously existed for the four-value `UserRole` enum; flagged explicitly in case the intended policy differs
- `GlobalExceptionHandler` gained `AccessDeniedException` → 403, with a message that never distinguishes "wrong role" from "not your resource" (ADR AZ03). No dedicated Spring Security `AccessDeniedHandler` was added — an interceptor-thrown exception resolves through the same `@ExceptionHandler` chain already in place, so a second handler would never fire
- **Tenant isolation gap closed:** `ConversationApplicationService.getConversation`, `.addUserMessage`, and `.addAssistantMessage` now take a `TenantId` and, after the existing `findByIdAndUserId` ownership-scoped fetch, verify it against the fetched conversation's own tenant — a mismatch resolves to the same `ResourceNotFoundException` (404) a nonexistent ID would, never a distinct "forbidden" outcome (ADR TN01, extending the exact pattern ADR R01 established for `PersistentConversationHistoryAdapter` in P04.13). `AddUserMessageCommand`/`AddAssistantMessageCommand` gained a `tenantId` field; `RagOrchestrationService` and `ConversationController` supply it from data they already have. Previously, tenant isolation for conversations relied entirely on the implicit, unverified invariant that a `UserId` belongs to exactly one `TenantId` forever
- **Ownership validation:** deliberately left exactly where it already was — `findByIdAndUserId`, pre-dating this milestone — rather than duplicated into `AuthorizationInterceptor`, which would mean querying the same repository twice per request (ADR OW01). `ADMIN` does **not** bypass ownership in this milestone — building cross-user read access for any role was out of scope and would deserve its own explicit design (ADR AZ03)
- No role, endpoint, or DTO leaked authorization logic outside `api.security`/`ConversationApplicationService` — controllers stay declarative (`@RequireRole` only), domain model untouched
- ADRs AZ01–AZ03, TN01, OW01 frozen (see `.claude/DECISIONS.md`)
- **Known, documented gap:** `ConversationApplicationService.renameConversation`/`.deleteConversation` did **not** get the same tenant check — both remain unreached by any REST endpoint today, so there's no live exposure, but the fix should land the moment either gets a route (tracked in `PROJECT_STATE.md`'s Deferred Items)
- 22 new tests: `AuthorizationInterceptorTest` (7) — no-annotation passthrough, missing/non-JWT authentication, matching/non-matching/multi-role decisions; `ConversationApplicationServiceTest` gained 8 tenant/ownership tests (wrong tenant on all three methods, correct tenant, not-found, same-tenant-different-owner); `ConversationControllerTest` net +5 (17 total) — role-denied (403) and role-permitted cases for both mutating endpoints, tenant-mismatch-returns-404-not-403 proof; `RagEndToEndIT` gained 3 tests against real Postgres — cross-tenant read denial, same-tenant-different-owner denial, and a VIEWER-role create denial that never reaches the database. 573 total tests, 0 failures. ArchUnit: 8/8 — no new layering violations (`AuthorizationInterceptor`/`RequireRole` stay in `api`; the tenant check stays in `application`, referencing only domain + `application.shared`)

### Added (P05.2 — Authentication Foundation)

Second milestone of Phase 5. Replaces P05.1's temporary permissive `SecurityFilterChain` (ADR O05) outright with real JWT authentication — every endpoint except login, health, and the OpenAPI/Swagger paths now requires a valid Bearer token, and `tenantId`/`userId` are no longer request-body fields anywhere in the API.

- `api.security` (new package) — `JwtTokenProvider` issues and verifies HS256 access tokens (ADR A01: symmetric key, matching the `security.jwt.secret-key` config already scaffolded ahead of this milestone; RS256 deferred); `JwtAuthenticationToken` is the sole `Authentication` type this app ever places in the `SecurityContext`, carrying `UserId`/`TenantId`/authorities; `JwtAuthenticationFilter` populates the context from the `Authorization: Bearer` header but never itself rejects a request — a missing or invalid token just leaves the context empty (ADR A04); `RestAuthenticationEntryPoint` is the single place a 401 RFC 7807 `ProblemDetail` is produced for an unauthenticated request to a protected endpoint
- `AuthController` (`POST /api/v1/auth/login`) — the sole token-issuing endpoint; verifies credentials via the new `AuthenticateUserUseCase` (`application.user`) and mints an access token via `JwtTokenProvider`. No refresh token, no logout, no revocation — access-token issuance only (ADR A02); `security.jwt.refresh-token-expiry-ms`, already scaffolded in `application.yml`, remains unused
- `AuthenticateUserUseCase` (`application.user`) — verifies email/password/tenantId/active-flag against the existing `UserRepository` port and a new `BCryptPasswordEncoder` bean (`infrastructure.config.PasswordEncoderConfig`); always throws the same `InvalidCredentialsException` regardless of which check failed (unknown email, wrong password, inactive account), so a caller cannot enumerate valid emails or tenants. Token minting stays out of this use case entirely — only `api.security.JwtTokenProvider` ever produces a JWT (ADR A03), keeping the application layer as technology-agnostic as every other use case in the codebase
- `SecurityConfig` rewritten — stateless session policy, CSRF stays disabled (unchanged rationale: no cookies), `permitAll` narrowed to exactly `/api/v1/auth/login`, `/actuator/health(/**)`, and the Swagger/OpenAPI paths; every other endpoint requires authentication
- `CreateConversationRequest`, `SendMessageRequest`, and the `GET /api/v1/conversations/{id}` `userId` query param all had their `tenantId`/`userId` fields removed — `ConversationController` now reads both from the authenticated `JwtAuthenticationToken` instead (ADR A05), fulfilling exactly what ADR O05 committed to in P05.1
- `GlobalExceptionHandler` gained one handler: `InvalidCredentialsException` → 401
- **Self-review fix (ADR A06):** `AuthenticateUserUseCase` originally short-circuited to `InvalidCredentialsException` for an unknown email without ever calling `PasswordEncoder.matches()` — a timing side channel (unknown-email requests returned faster than known-email/wrong-password ones) that could let an attacker enumerate valid emails/tenants despite both paths throwing the identical exception. Fixed before this milestone was called complete: the use case now always invokes `matches()`, comparing against a fixed dummy BCrypt hash when no user is found, equalizing cost across every failure path
- `security.jwt.secret-key` now has explicit non-production defaults in the `dev` and `test` Spring profiles (the base/production profile still has no default and fails fast at startup if `JWT_SECRET_KEY` isn't set — unchanged, intentional)
- `OpenApiConfig` gained a `bearerAuth` (HTTP Bearer/JWT) security scheme so Swagger UI's "Authorize" button can attach a token to requests it sends — without this, P05.1's existing Swagger UI would have become unusable for every protected endpoint the moment this milestone shipped
- **Known limitation, documented not silently worked around:** there is still no registration/admin endpoint — `RegisterUserUseCase` (Phase 1/2 foundation layer) remains unwired to REST, so a deployment must seed at least one user directly (migration or one-off script) before anyone can log in. Out of scope for "Authentication Foundation" per the milestone brief; tracked in `PROJECT_STATE.md`'s Repository Scope table
- ADRs A01–A05 frozen (see `.claude/DECISIONS.md`)
- 21 new tests: `JwtTokenProviderTest` (5) — sign/verify round trip with roles, expired token, tampered signature, malformed token; `JwtAuthenticationFilterTest` (4) — valid token populates context, missing/malformed header and invalid token all leave it empty without the filter itself producing a response; `AuthenticateUserUseCaseTest` (6) — success, unknown email, wrong password, inactive account (even with a correct password), proof that every failure path throws the identical exception, and proof the password encoder is invoked even for an unknown email (ADR A06's timing-leak fix); `AuthControllerTest` (4) — successful login, invalid credentials → 401, validation failures → 400, all against the real `SecurityConfig` chain proving `/login` is genuinely public; `ConversationControllerTest` net +2 (12 total) — added explicit unauthenticated-request → 401 coverage for all three endpoints, removed the now-nonsensical "missing tenantId field" test since the field no longer exists; `RagEndToEndIT`'s existing tests updated in place (still 2) — the full-turn test now authenticates with a real token minted by the real `JwtTokenProvider`, and the permissive-seam proof was rewritten to prove the opposite: an unauthenticated request is now rejected with 401. 551 total tests, 0 failures. ArchUnit: 8/8, `api.security` introduces no new layering violations (application still never depends on api; infrastructure still never depends on api)

### Added (P05.1 — End-to-End RAG Orchestration & REST Exposure)

First milestone of Phase 5 (Application Platform). Delivers the project's first complete path from an external HTTP request to a generated, cited, guardrail-checked, persisted answer.

- `RagOrchestrationService` (new `application.orchestration` package) — thin coordinator coupling `ConversationApplicationService`, `RetrievalService`, `ContextAssemblyPort`, and `GenerationService` for one full RAG turn: persist user message → retrieve → assemble context → generate → persist assistant message. No business logic of its own; none of its four collaborators were modified to support it (ADR O01)
- `ConversationApplicationService.addAssistantMessage(AddAssistantMessageCommand)` — closes the gap the P04.13 reconciliation identified and deliberately deferred (assistant replies were never persisted). Deliberately symmetrical with the existing `addUserMessage` (ADR O02)
- First REST API surface: `com.mudassirshahzad.eka.api` (new top-level package, matching the pre-existing but previously-vacuous ArchUnit `..api..` layering rules) — `ConversationController` at `/api/v1/conversations` (create conversation, get conversation detail, send message); every DTO is a record, no domain model ever crosses the wire; controllers only validate, convert, invoke, convert (ADR O03)
- `GlobalExceptionHandler` (`@RestControllerAdvice`) — centralized RFC 7807 `ProblemDetail` mapping using Spring 6's native `ProblemDetail` type (no new dependency): 404 for `ResourceNotFoundException`, 409 for `DuplicateResourceException`, 400 for validation/`IllegalArgumentException`, 502 for upstream pipeline failures (`GenerationException`/`RetrievalException`/`LlmException`), 500 generic fallback — no handler ever includes generated text, prompt content, or user query text in a response body (ADR O03)
- `SecurityConfig` — temporary, deliberately permissive `SecurityFilterChain` (`permitAll`, CSRF disabled for this stateless API). Exists specifically to prevent Spring Boot's default security auto-configuration from silently activating now that `spring-boot-starter-security` has its first consuming controller. ### Added (P04.7 — Context Assembly)

- `AssembledChunk` — immutable domain record carrying the full citation identity (`ChunkId`, `DocumentId`, `TenantId`), raw content, relevance score, and zero-based assembly position; position is distinct from `RetrievedChunk.rank()` — it records where the chunk appears in the assembled context, not where it appeared in raw retrieval output

### Added (P04.6 — Query Rewriting)

- `OllamaQueryRewriteAdapter` — first production implementation of `QueryRewritePort`; uses the Ollama chat model (temperature 0.1) to rewrite the user's query into retrieval-optimized terms before Hybrid Retrieval executes

### Added (P04.5 — Hybrid Retrieval Orchestration)

- `HybridRetrievalAdapter` — composite `RetrievalPort` that orchestrates vector and BM25 retrieval sequentially, concatenates results, and returns a unified `RetrievalResult` for downstream RRF ranking
- Sequential execution chosen over parallel: latency gain (~50ms) does not currently justify `CompletableFuture` complexity, exception semantics, and executor lifecycle overhead — documented for future upgrade when measured data justifies it
- Partial failure tolerance: if one engine fails, the surviving engine's results are used and `SearchMetadata.strategy()` reflects the degraded mode (`"hybrid:vector-only"` or `"hybrid:bm25-only"`); only total failure (both engines fail) raises `HybridRetrievalException`
- `HybridRetrievalException` — infrastructure exception thrown when both retrieval engines fail simultaneously
- `SearchMetadata` after fusion: `totalHits` = combined pre-deduplication count from both engines; `latencyMs` = total sequential retrieval wall-clock time; `strategy` = `"hybrid"` (or degraded variant) — `RetrievalService` preserves this metadata unchanged in the final ranked result
- Spring wiring: `HybridRetrievalAdapter` annotated `@Primary`; `WeaviateRetrievalAdapter` and `PostgresBm25RetrievalAdapter` annotated `@Qualifier("vectorRetrieval")` / `@Qualifier("bm25Retrieval")` — no new interfaces or `@Configuration` classes required
- `RetrievalService` promoted to `@Service` — now a Spring-managed bean automatically receiving `HybridRetrievalAdapter` as its `RetrievalPort`
- Duplicate handling: chunks appearing in both engine results are passed to RRF twice; deduplication and contribution accumulation remain the sole responsibility of `RrfRankingAdapter`
- 16 new tests in `HybridRetrievalAdapterTest` covering: both succeed, vector-only, BM25-only, both fail, empty results, ordering, duplicate passthrough, parameter propagation, sequential execution verification; 232 total tests, 0 failures

### Fixed (P04.AC1 Fix #1 — Eliminate Double-Embedding)

- **Critical bug fix**: chunks were embedded twice per ingestion — once by `EmbeddingService.embed()` and again unconditionally by `WeaviateVectorStore.doAdd()` inside Spring AI 1.0.0; this doubled embedding cost and silently discarded provenance-carrying vectors
- `VectorStore.index()` port signature changed from `index(List<Chunk>)` to `index(List<Chunk>, List<float[]>)` — callers supply pre-computed vectors and the vector store no longer triggers a second `EmbeddingModel.embed()` call
- `ChunkApplicationService.saveAll()` return type changed from `List<Chunk>` to `List<EmbeddedChunk>` — embedding vectors are preserved through the persistence step and forwarded to the indexing step
- `DocumentIndexingService.index()` parameter changed from `List<Chunk>` to `List<EmbeddedChunk>` — extracts `Chunk` and `float[]` lists and passes pre-computed vectors directly to `VectorStore.index()`
- `WeaviateVectorStoreAdapter.index()` rewritten: bypasses `springVectorStore.add()` entirely; calls the Weaviate Java client batch API directly with pre-computed vectors and replicates Spring AI's storage format (`content`, `metadata`, `meta_*` fields) so that `search()` — which still delegates to Spring AI — deserialises results correctly

- 10 new regression tests in `WeaviateVectorStoreAdapterTest` verify: Weaviate client (not Spring AI) is called; pre-computed vectors are forwarded exactly; vectorId is assigned post-success; vectorId is not assigned on batch failure; content and `meta_*` properties are stored; mismatch between chunk/vector counts is rejected; search still delegates to Spring AI; null filter expression is safe; 216 total tests, 0 failures

### Added (P04.4 — Reciprocal Rank Fusion)

- Production `RrfRankingAdapter` — first `RankingPort` implementation; merges multiple ranked retrieval lists using Reciprocal Rank Fusion (Cormack et al. 2009)
- RRF formula: `score = Σ (1 / (k + rank_i))` summed over all retrieval engine occurrences of each chunk; `k` defaults to 60 and is configurable via `app.retrieval.rrf-k`
- Duplicate chunk fusion: chunks appearing in multiple retrieval lists are merged by `ChunkId`; RRF contributions accumulate and metadata is preserved from the first occurrence
- Max-normalization of raw RRF scores to `[0.0, 1.0]` satisfying the `RetrievedChunk.score` contract; the highest-scoring chunk in each fused result set maps to `1.0`
- Deterministic tie-breaking: equal RRF scores resolved by ascending lexicographic order of `ChunkId` UUID — stable across JVM restarts
- Output rank semantics: `RetrievedChunk.rank` in the fused output is the zero-based position in the RRF-ranked list; original per-engine ranks are consumed as formula inputs
- 24 new automated tests covering mathematical correctness, duplicate accumulation, score normalization, tie-breaking, k-value sensitivity, and the classic two-list fusion example; 206 total tests, 0 failures
